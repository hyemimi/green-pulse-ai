# 2단계 결함 탐지·유형 분류 구조

## 전체 구조

이 프로젝트는 이진 분류만 수행하는 모델이 아니다. 최종 문제는 다음 두 모델로 분리했다.

```text
1분 센서 데이터
  ↓
[1단계] HGB 이진 탐지
정상 vs 결함, 결함 확률
  ↓ 경보 발생
[2단계] Extra Trees 온라인 유형 분류
F1·F2·F3·F4 유형별 확률
  ↓
대시보드: 경보 단계 + 추정 결함 유형 + 설명 센서
```

1단계는 결함을 가능한 빨리 찾는 모델이고, 2단계는 발견한 결함이 어떤 유형인지 진단하는 모델이다. 두 과제를 분리한 이유는 결함 여부와 유형 분류의 평가 단위와 필요한 관측 시간이 다르기 때문이다.

## 1단계: 결함 여부 탐지

| 항목 | 내용 |
|---|---|
| 모델 | Histogram Gradient Boosting |
| 정답 | `is_fault` = 정상 0 / 결함 1 |
| 입력 | 현재·과거 센서로 만든 176개 인과적 특징 |
| 실행 주기 | 반응기별 1분 |
| 직접 출력 | `fault_probability` |
| 평가 | 이벤트 탐지율, 최초 경보 지연, 정상 오탐/반응기·24h |

개발 기준선은 확률 0.35 이상이 2분 연속 유지되면 경보한다. Test 8개 이벤트를 모두 탐지했고 중앙 지연은 30분이었다. 전체 90일 재생 오탐은 1.308건/반응기·24시간으로 목표를 넘어 배포는 보류했다.

다단계 운영 정책에서는 같은 HGB 확률을 다음처럼 해석한다.

| 단계 | 규칙 | Test 중앙 지연 | 정상 경보/반응기·24h |
|---|---|---:|---:|
| 이상 징후 | 0.225 이상 1분 | 26.5분 | 4.612 |
| 조기 경고 | 0.250 이상 2분 | 29.5분 | 1.936 |
| 확정 경보 | 0.450 이상 2분 | 32분 | 0.957 |

## 2단계: 결함 유형 분류

| 항목 | 내용 |
|---|---|
| 모델 | Extra Trees 온라인 유형 분류기 |
| 정답 | `fault_type` 1~4 |
| 입력 단위 | HGB 경보 이후 매분 시점 |
| 입력 | 6시간 기준 특징 24개 + 물리 관계 특징 5개 |
| 직접 출력 | F1~F4 클래스별 확률과 현재 임시 유형 |
| 평가 | 이벤트 단위 accuracy와 macro F1 |

유형 클래스는 다음과 같다.

| 코드 | 결함 유형 | 대표 패턴 |
|---|---|---|
| F1 | Cooling System Degradation | 온도 상승 + 냉각수 유량 감소 |
| F2 | Feed Flow Blockage | 원료 유량 감소 + 전환율 감소 |
| F3 | Sensor Drift | 온도 변화 + 관련 센서와의 물리적 불일치 |
| F4 | Mechanical Wear | 진동 RMS 상승 + 모터 전류 상승 |

### 온라인 유형 모델의 29개 입력 특징

12개 센서에 대해 다음 두 인과적 기준선 특징을 만든다.

- 현재값의 과거 6시간 기준 z-score
- 15분 평균의 과거 6시간 기준 z-score

F1·F3 구분과 다른 유형의 물리 조합을 위해 다음 5개 관계 특징을 추가한다.

```text
냉각 패턴 = 온도 z - 냉각수 유량 z
온도-공정 불일치 = 온도 z - 평균(반응률·전환율·압력 z)
유량-전환율 결합
진동-전류 결합
온도×냉각수 반대 방향 곱
```

Train 이벤트의 HGB 경보 후 0~60분 행으로 학습하고 Validation의 경보 후 0·5·10·15분 macro F1 평균으로 모델을 선택했다. Extra Trees가 선택됐으며 매분 유형 확률을 갱신할 수 있다.

| 평가 | 결과 |
|---|---:|
| 경보 즉시 Validation macro F1 | 0.667 |
| 경보 즉시 Test macro F1 | 0.867, 7/8 |
| 경보 10분 후 Validation macro F1 | 1.000, 8/8 |
| 경보 10분 후 Test macro F1 | 1.000, 8/8 |
| 중앙 10분 확인 시점 | 결함 시작 후 약 40분 |

10분 시점에는 F1과 F3도 모두 구분했지만 유형별 Test가 2개뿐이고 예측 확률이 낮다. 100%를 안정적인 일반화 성능으로 주장하지 않는다.

## 왜 한 모델로 F0~F4를 바로 분류하지 않았나?

- 정상 행이 압도적으로 많아 다중 클래스 모델이 정상 분류에 치우칠 수 있다.
- 결함 탐지는 매분 빠르게 수행해야 하지만 유형 진단에는 변화가 누적될 시간이 필요하다.
- 이진 탐지에는 오탐과 지연이 중요하고 유형 분류에는 클래스별 재현율과 macro F1이 중요하다.
- 탐지 임계값과 대응 정책을 유형 모델과 독립적으로 조정할 수 있다.

따라서 1단계는 민감한 결함 탐지, 2단계는 이벤트 단위 진단으로 역할을 분리했다.

## 대시보드 출력 시점

```text
정상 운전
  → HGB 확률만 계속 갱신

이진 경보 발생
  → alert_stage 표시
  → 물리 패턴 기반 임시 유형 힌트

경보 후 매분
  → F1~F4 확률과 임시 유형 갱신

경보 후 10분
  → Validation 기준 확인 후보
```

경보 직후에도 유형은 출력되지만 초기 정보가 적으므로 임시 후보로만 해석한다.

## 실시간 출력의 제한

온라인 모델은 경보 시점부터 출력되지만 분마다 유형이 바뀔 수 있고 최대 클래스 확률도 낮다. 따라서 즉시 결과는 `provisional`, 10분 결과는 `confirmed_candidate`로 표시하고 자동 정비 명령에는 사용하지 않는다. 확률 calibration과 최근 여러 분의 예측을 합치는 시간적 안정화가 후속 과제다.
